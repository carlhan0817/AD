# 屏幕比例适配 设计文档

日期:2026-11-06
状态:待用户审阅(已过一轮审阅者检查;标「写文档时代为决定」的可改)

## 一、要做成什么样

程序要发给朋友用。朋友的屏幕可能是 2K、4K、笔记本、带鱼屏(宽屏),也可能接近正方形(4:3、5:4)。也有人在窗口模式下把 Dota 窗口开成各种大小。在这些情况下,技能池、英雄格、玩家卡都要认准,推荐框也要画在对的位置上。

不支持的比例在 GitHub 项目页(中英文两份 README)写明。

## 二、现状(查过代码和数据)

- 所有位置都是按 1920×1080 标的:`core/src/recognition/pool_slots.ts`(48 格)、`hero_layout.ts`(12 英雄格,含 `HERO_OFFSET_1080P` dy=-4 的修正)、`player_cards.ts`(10 张卡 + 40 个已选格)。
- 遇到别的尺寸时,横纵各自按 宽/1920、高/1080 拉伸。
- 仓库根的 `layout_coordinates.json`(源自上游 ability-draft-plus,ISC)有 28 种分辨率的位置。拿它和 1080p 做线性拟合的结果:
  - **16:9**(1176×664 到 3840×2160):等比缩放,误差 ±1 像素。**现在的算法已经对。**
  - **21:9 / 2.33–2.4**(1834×786、3440×1440、3840×1600):按高度缩放 + 水平居中(x 偏移 = 宽/2 − 960×高/1080),技能池和玩家卡都符合。
  - **16:10、3:2、1.56、1.67、4:3、5:4**:玩家卡大致是"按高度缩放 + 居中",但技能池明显不是简单缩放,横向排布变了。同一类比例内,横向系数与高度成正比(16:10 一类约 0.475×高/1080,4:3 和 5:4 约 0.396×高/1080),说明每一类比例有固定布局,只是按高度缩放。上游这几类数据的准确度没验证过,而它在 1080p 上就和我们实测有偏差(英雄格要 dy=-4)。
- 用户自己的电脑:1920×1080 显示器,系统缩放 125%,只能在窗口模式下开出比屏幕小的尺寸;2K、4K、带鱼屏开不出来。

## 三、目标 / 不做的 / 绝不能出现的

**目标**
1. 16:9 任意大小(1280×720 到 3840×2160)认准。
2. 21:9 带鱼屏认准。
3. 16:10、3:2、4:3、5:4 认准(这几类以用户在自己电脑窗口模式下截的真实图为准)。
4. 窗口模式下的任意窗口大小:只要比例落在支持的类里就认准。
5. 不支持的比例:不乱认、明确提示,并在 GitHub 页面写明支持哪些比例。

**这次不做**
- 不改识别方法本身(分类器、按组认英雄、记忆、变化检测阈值、打分都不动),只改"去哪里截格子"。
- 不支持独占全屏(早先已定:只读检测后引导切换无边框/窗口)。
- 不做多显示器(Dota 不在主屏上时)——如果顺手能支持再说。

**绝不能出现**
- 比例没对上时硬着头皮认,把错位的格子当真写进本局记忆、给出错推荐。
- 已经认准的 1920×1080 变差(现有真机帧回归测试 `main/tests/capture/runtime_frames.test.ts`、`board_change_frames.test.ts` 必须照常通过)。

## 四、已经定下来的做法

### 1. 按比例分类,每类一张位置表,按高度缩放、水平居中(用户确认方向)

- 程序拿到游戏客户区宽高,算宽高比,归到最接近的一类:16:9、21:9、16:10、3:2、4:3、5:4。
- 每一类有自己的一套位置(技能池 48 格、英雄格 12、玩家卡 10、卡上已选格 40,以及高亮框要避开的区域),以该类的一个"基准高度"标出。
- 实际位置 = 基准位置 × (实际高度 / 基准高度),再水平居中到客户区里。
- 2K、4K、笔记本只要比例相同就共用一张表;窗口模式下的任意窗口大小也走同一套规则。
- 16:9 那张表就是现在 1080p 的表(不改数值),这样 1080p 的结果不变。现有「近 1080p(±10 像素)按原样不缩放」的规则保留在 16:9 类里。*(写文档时代为决定)*
- 每一类是一整套独立的表(技能池、英雄格、玩家卡、已选格各自的位置),不是一个通用公式套出来的:技能池在 16:10、4:3 这些比例下是重新排布的。「按高度缩放 + 居中」只是把这一类的基准表换算到实际窗口大小。21:9 例外:它的表由 16:9 的表按公式推出。*(写文档时代为决定)*
- 21:9 那张表先按公式从 16:9 推出,用上游 3440×1440、3840×1600 的数据核对。

### 2. 16:10、3:2、4:3、5:4 用用户自己的真实截图标定(用户确认)

- 用户在自己电脑上把 Dota 设成窗口模式,依次开以下尺寸,各进一局自定义 AD 的选人界面,用热键截图(开发版热键扫描会存帧):
  - 16:10:1440×900(或 1280×800)
  - 3:2:1440×960
  - 4:3:1280×960(或 1024×768)
  - 5:4:1280×1024(高度可能被任务栏挡,开不出就跳过,用上游数据 + 4:3 推)
  - 16:9 小窗:1280×720(验证小尺寸下分类器还认得准)
- 每个尺寸最好截两张:选人刚开始(满池)一张,中途有空格、卡上有已选的一张。
- 标定以识别结果为准,而不是以目测框对没对齐为准(项目以前吃过亏:目测对齐和算法最优会冲突,以算法为准)。上游数据当初值。

### 3. 不支持的比例

- 归类从严:实际宽高比和某一类相差 2% 以内才算这一类;夹在两类之间的(比如 1.56、1.63)算不支持,不硬套最近的一类。*(写文档时代为决定;Dota 设置里能选的分辨率基本都落在这六类上,夹在中间的多是手动拖出来的窗口)*
- 宽高比离六类都太远(例如 32:9 超宽、窗口被拖成竖长条):不扫描、不写记忆,悬浮窗提示「当前屏幕比例暂不支持,请看项目主页」,日志记一行实际宽高和比例。*(写文档时代为决定)*
- 中英文 README 加一节「支持的屏幕」:列出支持的比例和常见分辨率举例,写明不支持的情况(比例不在列表里、独占全屏、多显示器 Dota 不在主屏)。

### 4. 位置算错时的安全网

比例对了,位置也可能不准,尤其是没有真机截图验证的类(21:9,可能还有 5:4)。现有的「选人界面检查」就是安全网:识别结果里认得出的格子不到一半、空格数和卡上已选数对不上、找不到我的绿框,这一帧就不写记忆。位置错位时这几条会挡住,不需要另做一套。没实测的类照样扫描,README 里标「按公式/上游数据支持,未实测」。*(写文档时代为决定)*

### 5. 分批合并

先合:比例归类、16:9、21:9、不支持提示、README;等用户截完图、标定好、真机验收过 16:10 和 4:3 再合这几类的表。还没标定的类在 README 里标「未实测」。*(写文档时代为决定)*

## 五、现有代码里能用上的

- `layout_coordinates.json` 的 28 种分辨率数据(上游初值)。
- 三个位置模块都已经接收 `ClientRect` 参数,调用方不用改。
- 现有工具:`core/src/recognition/classifier.ts`(可逐格看置信度)、`pool_classify.ts`(读 48 格)、`card_reading.ts`、`hero_taken.ts`;本地真机帧在 `app/.scan_frames/`(含玩家名,只留本地)。
- `app/src/main/index.ts` 里 `currentGameRect()` 每次扫描读一次客户区,窗口改大小后下一次扫描就用新尺寸。客户区来自只读的 `GetClientRect` + `ClientToScreen`(`main/src/ffi/game_window.ts`),不含标题栏和边框,是物理像素(125% 缩放下真机日志显示 1920×1080);截图是整个主屏的物理像素,按客户区的位置去截。窗口模式下这一点要在真机上核对一次(截图里找客户区左上角)。
- 悬浮窗位置已经按客户区摆放并做了系统缩放换算(`overlayBoundsFor` → `rectToOverlayBounds` + `screen.screenToDipRect`),窗口模式下跟着走,不需要另做。
- 也要跟着新位置走的:`core/src/recognition/highlight.ts`(推荐框,现在按 宽/1920 缩放),以及用到这些位置的变化检测(`board_change.ts`)、英雄格「已选」判断(`hero_taken.ts`)、卡片读取(`card_reading.ts`)。
- 不用改的:早期连续监控留下的 `layout_derive.ts`、`roi.ts` 里的 `poolCellRects`/`diffRois`(只在 `AD_MONITOR_LOOP=1` 时用,是保留资产,不在这次范围内)。
- 显示比例归类结果后,`app/src/main/display_mode_guide.ts` 一类的引导文案机制可以借用来做「不支持」提示。

## 六、交给实现者决定的

- 比例归类的容差(离多远算「不支持」)。
- 位置表的存放形式(沿用 TS 常量表,或改成读 JSON)。
- 标定的具体办法(在截图上搜偏移/缩放让分类器置信度最高之类),以及小尺寸下若分类器认不准怎么办(先报告,不擅自改识别)。
- 21:9 的真机验证:用户电脑开不出来,能否用缩小的截图合成近似验证,或在 README 里标为「按公式支持、未实测」。
- 高亮框、玩家卡绿框/金卡判断等依赖位置的地方,跟着同一套位置走。

## 七、怎么算做完

1. 单元测试:比例归类;每类按高度缩放 + 居中的换算;16:9 在 1920×1080 下与现在的位置逐个相同。
2. 用用户截的每种尺寸真实帧做回归测试(缺帧就跳过,和现有真机帧测试一样):48 格识别结果、英雄格、我坐哪、轮到谁都对。
3. 现有测试、合规扫描、构建全部通过;1920×1080 真机帧回归不变。
4. 真机:用户在至少 16:10 和 4:3 两种窗口尺寸下各打一局,自动扫描全程认对、框画对。
5. 中英文 README 写明支持和不支持的屏幕。
