# 全自动扫描 设计文档

日期:2026-11-05
状态:待用户审阅(已过一轮审阅者检查;标「实现者的决定」的是写文档时代为拍板的,用户可改)

## 一、要做成什么样(用户原话的意思)

进入选人界面后,玩家只管挑技能,别的都自动:不用按热键,别人每选一手、轮到谁变了,悬浮窗上的推荐和技能池上的框都自己跟着变。热键 `Ctrl+Shift+S` 保留,玩家随时可以自己扫一次。

## 二、为什么现在做

- 识别、记忆、打分、在画面上标框、GSI 自动出现/隐藏都已经做好并在真机上跑通。现在唯一要人手动做的事就是每手按热键。
- 之前调推荐权重要靠用户每手截图;自动扫描以后每局都留下完整记录,后面调权重才有依据。

## 三、目标 / 不做的 / 绝不能出现的

**目标**
1. 选人阶段自动识别并刷新推荐,玩家不用碰键盘。
2. 开了 GSI 的玩家:选人以外的时间一张图都不截。
3. 没开 GSI 的玩家也能用自动扫描,且在游戏里不卡。
4. 轮到「我」的时候推荐不在眼前乱跳。
5. 热键扫描一直可用。

**这次不做**
- 不改识别逻辑(分类器、按组推英雄、记忆规则都不动),不改打分公式和权重。
- 不支持 1920×1080 以外的分辨率。
- 不做安装包。

**绝不能出现(出现了就算失败,哪怕功能「能用」)**
- 游戏里(非选人阶段)出现可感知的卡顿。
- 轮到我时,推荐或框在我准备点的时候跳走。
- 过渡画面(动画中途、弹窗、加载画面)被写进本局记忆。
- Dota 没开时还在截图。
- 任何替玩家点击、选取的行为(合规红线:不模拟输入,只读屏幕)。

## 四、已经定下来的做法(用户确认过)

### 1. 什么时候扫

| 情况 | 做法 |
|---|---|
| 开了 GSI,阶段是 `INIT` / `WAIT_FOR_PLAYERS_TO_LOAD` / `HERO_SELECTION` | 自动扫描开着 |
| 开了 GSI,其他阶段(策略时间、游戏中、结束、主菜单「不在对局里」) | 完全不截图 |
| 没开 GSI(或 GSI 超过 30 秒没数据) | Dota 窗口在就每 3 秒看一眼;看到选人界面就进入自动扫描;连续 2 次不是选人界面就退回「每 3 秒看一眼」 |
| Dota 窗口在,但不在最前面(玩家切到了别的窗口) | 截到的不是 Dota,这一帧直接跳过,**不算**「不是选人界面」(不会因此停掉自动扫描或隐藏悬浮窗)|
| Dota 窗口不在 | 完全不截图 |
| 任何时候按热键 | 立刻扫一次 |

「每 3 秒看一眼」只做一个很轻的「是不是选人界面」检查,不跑完整识别(完整识别要对 48 格加玩家卡跑分类器,在游戏里每 3 秒跑一次没测过开销)。确认是选人界面后才进入自动扫描、跑完整识别。这是在识别前面加一道门,不改识别本身。*(实现者的决定)*

Dota 在不在最前面用只读的 Win32 查询判断(例如 `GetForegroundWindow` 对比 Dota 窗口句柄),不对 Dota 窗口做任何写操作,符合合规红线。*(实现者的决定)*

说明:加载(`INIT`)和等待玩家加载(`WAIT_FOR_PLAYERS_TO_LOAD`)也要扫,是因为真机日志里这两个阶段能持续约 40 秒,而选人画面可能在 GSI 报 `HERO_SELECTION` 之前就出来了。截到的不是选人界面会被现有的「选人界面检查」挡掉,不会写进记忆。

### 2. 托盘开关

托盘菜单加一个「自动扫描」勾选项,默认打开,设置要记住(下次启动沿用)。关掉后只用热键。没开 GSI 时,托盘里提示「启用 GSI 可以省掉游戏里的截图开销」。

### 3. 推荐什么时候变(「锁」)

- 没轮到我:画面变了(有人选走一格、轮到的人变了)就重新识别并刷新推荐。
- 轮到我:这一回合刷新一次后**锁住**,推荐和框不再变,直到我选完(我的卡上多了一格,或者轮到的人变成别人)才解锁。
- 锁住期间照常扫描、照常更新本局记忆,只是不把新推荐推给悬浮窗。
- 热键扫描不受锁限制:按了就刷新。
- 「我」坐哪认不出来时(`myRow` 为空),没法判断是不是轮到我,就不锁。
- **第一次读不完整时允许再改一次**(用户确认):轮到我后第一次刷新时,如果有池格没认出、我的卡没读全,或者画面被挡住,那么之后第一次读完整的结果可以再刷新一次,然后锁死,直到我选完。
- 「轮到谁」偶尔读不出来(读成空)不算换人,不解锁;只有读到明确是别人,或我的卡上多了一格,才解锁。*(实现者的决定)*

### 4. 截图方式:统一改用画面流

**真机实测**(2026-11-05,1920×1080,无边框窗口,英雄演示模式站泉水,基准 115–117 FPS,每 3 秒截一次):

| 方式 | 每次截图耗时 | 本程序 CPU | 游戏里的感受 |
|---|---|---|---|
| 普通截图,全分辨率(现在热键用的) | 平均 0.9–1.0 秒,最慢 2.4 秒 | 2–4% | **每次截图游戏顿一下** |
| 普通截图,缩到 480×270 | 平均 0.9–2.0 秒,最慢 3.6 秒 | 3–4% | **一样顿** |
| 持续画面流,全分辨率 | 平均 0.19 秒(第一次 1.2 秒是开通道) | 2.4% | **不卡** |

结论:卡顿来自「每次整屏抓一遍」,缩小也没用;画面流一直开着通道、取帧只是拿一张,不卡。所以:

- 自动扫描和热键扫描都用画面流(现有的 `captureViaStream`,目前要设 `AD_STREAM_CAPTURE=1` 才用;改成默认)。
- 画面流失败才退回普通截图(现有的退回逻辑保留)。
- 选人阶段用普通截图实测 FPS 也没明显变化,所以退回时不会出大问题。

**画面流颜色有偏差,要先验证识别**:画面流经过视频编码,颜色和普通截图有小差异(早先实测平均差 2 个亮度级,所以当初默认没开它)。上面的实测只量了耗时和 FPS,没量识别准不准。动手第一步:同一画面用两种方式各截一张,分别跑 `scanPool`,对比每格结果、选人界面检查和英雄格「已被选」判断。*(实现者的决定)*
- 一致:两种扫描都用画面流。
- 不一致:分工。画面流只用来「看画面变没变」和选人以外的低频查看;真正识别时在选人阶段用普通截图(选人阶段普通截图不影响 FPS,已实测)。不为了迁就画面流去改识别阈值。

### 5. 每次看一眼之后怎么决定要不要识别

- 选人阶段大约每秒取一帧。
- 只比较会因为「有人选了东西」而变的区域:技能池 48 格、12 个英雄格、10 张玩家卡上的已选格、「轮到谁」的标记。
- **不能**把每秒都会变的东西算进来:中央倒计时、玩家卡上的倒计时徽章、闪烁的边框、鼠标悬停弹出的说明框。项目里吃过两次这个亏(比较区域里含了倒计时,画面就永远「在变」)。
- 画面变了以后,等它静止下来(动画播完)再识别,不识别动画中途的半截画面。
- 鼠标:画面流尽量请求不带鼠标指针。轮到我时鼠标常在池子上移动、悬停说明框会盖住格子,画面可能一直不静止;所以超过约 3 秒还不静止,就照样识别一次(这次读不完整的话,按上面「允许再改一次」处理)。*(实现者的决定)*
- 悬浮窗自己画的推荐框在所有识别区域外面(外扩 5 像素、粗 3 像素),所以比较区域只取识别区域,就不会把自己画的框当成「画面变了」。
- 识别本身沿用现有的 `scanPool`,结果和热键扫描完全一样处理(写记忆、打分、推悬浮窗、存帧、写日志)。

### 6. 悬浮窗显示规则的配套调整

- GSI 在 `INIT` / `WAIT_FOR_PLAYERS_TO_LOAD` 阶段,和「不在对局里」一样改看画面:最近一次扫描是选人界面就显示。(现在这两个阶段一律隐藏。)
- GSI 说在选人,但连续 2 次扫描都不是 AD 选人界面(比如打的是普通模式),隐藏。

## 五、现有代码里能用上的

- `app/src/main/index.ts`:`startManualScan` 里的 `scan()` 是完整的一次扫描(截图 → `scanPool` → 记日志 → 推悬浮窗),已有 `busy` 防重入。
- `app/src/main/presence.ts`:`OverlayPresence` 管 GSI 状态、显示/隐藏、托盘菜单,已有每 5 秒的复查定时器和 Dota 窗口检测。
- `core/src/gsi/gsi.ts`:GSI 解析、`GsiTracker`、`decideOverlay`。
- `core/src/recognition/frame_diff.ts`:`FrameGate`(按区域 hash 判断画面变没变 + 等静止再放行),是早期连续监控留下的,可以参考或复用;注意它比较的是精确 hash,真机画面可能有细微抖动。
- `app/src/preload` 里的画面流:一直开着,60 秒没人取帧就自动关。
- `main/src/capture/scan_pool.ts` 返回的 `onDraftScreen`、`myRow`、`activeRow`、`myPicks`,够判断「轮到我」和「我选完了」。
- 本地存的真机帧在 `app/.scan_frames/`(含其他玩家名字,只留本地,不进仓库),可以拿来做比较区域的回归测试。

## 六、交给实现者决定的

- 比较区域的具体坐标、「变了」的判断方式(精确 hash 还是允许小误差的像素差)和阈值,以真机帧验证为准。
- 「静止」要等几帧、取帧间隔的精确值(大约每秒一次即可)。
- 自动扫描的调度逻辑放在哪(建议做成 `core` 里的纯逻辑,方便用假时钟测试)。
- 设置文件的组织方式(和 `gsi.json` 合并还是分开)。
- 存帧细节。已定原则:只在真正跑了识别时存;按局分文件夹,只留最近 5 局。日志每局完整保留,够调权重用。现在 80 张约 202MB,不限制会撑满硬盘。*(实现者的决定)*
- 日志格式:至少记下自动扫描的开始/停止及原因、每次触发识别的原因、锁住/解锁。

## 七、怎么算做完

1. 单元测试:调度(什么时候扫、什么时候停、锁和解锁)用假时钟测;比较区域用本地真机帧测「同一局面的连续帧不算变化,有人选走一格算变化」。
2. 现有测试、合规扫描、构建全部通过。
3. 真机:
   - 开着 GSI 打一局完整的 AD,全程不按热键,每手推荐都对,轮到我时推荐不跳,进游戏后日志里没有截图记录。
   - 关掉 GSI 再打一局,自动扫描照样工作;在英雄演示里站泉水,FPS 和基准(115–117)比没有可感知的卡顿。
4. 删掉临时测量代码 `app/src/main/watch_spike.ts` 及 `index.ts` 里接它的几行。
